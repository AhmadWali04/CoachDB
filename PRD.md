# Rival Coaches --- MVP Product Requirements Document

**Status:** Build specification\
**Version:** 1.0\
**Product type:** AI multi-agent soccer coaching competition\
**Primary goal:** Demonstrate two independent AI coaches that observe
the same simulated match, make competing tactical decisions at halftime,
learn from match history, survive worker failures, and communicate
coaching decisions with ElevenLabs voice.

------------------------------------------------------------------------

## 1. Product summary

Rival Coaches is a self-contained soccer simulation in which two AI
coaching systems manage opposing teams. Each coach receives the same
match observations from its own team's perspective, analyzes the first
half, predicts the opponent's likely adjustments, and submits structured
tactical instructions for the second half.

A deterministic/probabilistic simulation engine---not an LLM---executes
the match. MongoDB Atlas stores authoritative match state, events,
decisions, action status, checkpoints, and coaching experiences. Atlas
Vector Search retrieves relevant past experiences. A recovery controller
detects stalled workers and resumes from verified state. ElevenLabs
turns approved coaching messages into audio.

The MVP is successful when the system can run a complete match, make
both coaches' decisions visibly affect the second half, explain and
speak the decisions, recover from a simulated crash, and produce a
reproducible comparison report.

## 2. Goals

1.  Run a complete simulated match with two opposing teams.
2.  Give each coach an independent analysis and tactical decision
    process.
3.  Make halftime decisions change simulation parameters and therefore
    influence match events.
4.  Let each coach model and anticipate the opposing coach.
5.  Persist verified progress and recover safely after a worker crash.
6.  Retrieve relevant prior coaching experiences using MongoDB Atlas
    Vector Search.
7.  Evaluate coaching quality across repeated matches, not only final
    score.
8.  Generate optional ElevenLabs audio for halftime briefings and key
    coaching commentary.

## 3. Non-goals

Do **not** build these in the MVP:

-   Integration with live professional matches, video feeds, wearables,
    or real club systems.
-   Full 11-player physics, animation, or a production-grade football
    simulator.
-   Autonomous substitutions, injuries, transfer markets, training,
    season management, or player careers.
-   Coaches changing tactics continuously during every simulation tick.
-   Coaches accessing each other's private chain-of-thought, prompts, or
    internal memory.
-   Training/fine-tuning custom models.
-   A public multiplayer product or user accounts.
-   Treating LLM-generated claims as match facts.
-   Requiring MongoDB Change Streams or Stream Processing for the
    initial version.

## 4. Users and core experience

**Primary user:** Hackathon judge or demo participant.

The user should be able to: 1. Start a match or a batch of matches. 2.
Watch a simple pitch/dashboard with score, clock, possession, shots, and
recent events. 3. See both coaches' halftime analysis, predictions, and
tactical instructions. 4. Hear a short voice briefing generated by
ElevenLabs. 5. Watch the second half respond to the tactical changes. 6.
Inspect the post-match comparison and evidence behind the scores. 7.
Trigger a controlled worker crash and see recovery without replaying
completed actions.

## 5. Match and simulation rules

### 5.1 Match format

-   Two teams, fixed roster and player attributes for the MVP.
-   Two halves, each containing a configurable number of simulation
    steps (default: 20).
-   Halftime occurs after the first half.
-   Each coach submits one tactical plan at halftime.
-   No further tactical changes during the second half in the initial
    MVP.
-   Use a seeded random number generator. Store the seed so a match can
    be reproduced.
-   The simulation engine owns the authoritative clock, score, events,
    player availability, and tactical state.

### 5.2 Minimum match state

Each team has: - Formation: `4-3-3`, `4-2-3-1`, or `4-4-2`. - Mentality:
`balanced`, `attacking`, or `defensive`. - Pressing: `low`, `medium`, or
`high`. - Defensive line: `low`, `medium`, or `high`. - Attack focus:
`middle`, `left`, or `right`. - Tempo: `slow`, `normal`, or `fast`.

Each player has a stable ID, role, skill ratings, stamina, and
availability. The MVP can use a small abstract roster rather than model
every real-world position in detail.

### 5.3 Simulation behaviour

The simulation should use transparent, testable rules. Tactical settings
must affect event probabilities or outcomes. At minimum: - High pressing
can increase turnovers and pressing-related stamina loss. - High
defensive line can support pressure but increase vulnerability to balls
in behind. - Attacking mentality/fast tempo can increase attacking
opportunities and turnovers. - Defensive mentality can reduce opponent
opportunities while reducing own attacking volume. - Attack focus can
influence where attacks are generated. - Fatigue reduces relevant
player/team effectiveness.

Do not claim that the simulation is a realistic professional football
model. Label it as a simplified tactical simulator.

### 5.4 Match event types

At minimum: `pass_sequence`, `turnover`, `shot`, `goal`, `save`,
`possession_change`, `pressing_success`, `counterattack`, `foul`, and
`half_time` / `full_time`.

Every event has a unique ID, match ID, half, step/time, team ID (where
applicable), event type, structured details, and creation timestamp.

## 6. AI coaching system

Each coach is independent and receives: - Its own team's performance
summary. - Opponent performance summary visible from match events. -
Current match state and player/team condition. - A limited set of
relevant retrieved experiences. - The public match observations
available to both teams.

Each coach must return validated JSON conforming to the same schema. No
free-form text may directly control the simulation.

### 6.1 Minimum agent roles

Keep the number of agents small for reliability and latency.

**Per coach:**

1.  **Match Analyst**
    -   Summarizes first-half evidence from structured events and
        statistics.
    -   Identifies strengths, weaknesses, and trends.
    -   Must cite event IDs or metric values for factual claims.
2.  **Tactical Coach**
    -   Combines own-team analysis, opponent analysis, retrieved
        experiences, and an opponent prediction.
    -   Produces one valid second-half tactical plan and a short
        rationale.
    -   Predicts the rival coach's likely adjustment with a confidence
        score and evidence.
3.  **Execution/Verification Worker**
    -   Validates the plan against allowed options and current state.
    -   Submits it using an idempotent action ID.
    -   Reads back the applied simulation state and records verified
        success.

**Shared non-LLM services:** - Match simulator. - Recovery controller /
worker supervisor. - Evaluation harness. - ElevenLabs speech service. -
MongoDB repository and Vector Search adapter.

The rival coach uses the same architecture and constraints but has
separate identity, prompt configuration, and private memory namespace.

### 6.2 Coach output contract

A coach plan must be machine-readable and validated:

``` json
{
  "match_id": "match_001",
  "team_id": "blue",
  "formation": "4-2-3-1",
  "mentality": "attacking",
  "pressing": "high",
  "defensive_line": "medium",
  "attack_focus": "left",
  "tempo": "fast",
  "opponent_prediction": {
    "likely_change": "lower defensive line",
    "confidence": 0.72,
    "evidence": ["event_014", "metric:through_ball_attempts"]
  },
  "rationale": "Short evidence-based explanation.",
  "risks": ["Higher stamina consumption"],
  "expected_effects": ["More left-side entries", "More turnovers under pressure"]
}
```

All enum values, IDs, and confidence ranges must be validated. Reject
malformed or unsupported actions and request one bounded correction; if
still invalid, use a safe balanced default and record the fallback.

## 7. Rival intelligence and competitive learning

-   Coaches may predict the rival's likely tactical change based on
    observed match behaviour and their own historical records.
-   Coaches must not access the rival's private prompts, hidden
    reasoning, or private memory.
-   The evaluator records predicted versus actual rival changes.
-   Across a series, each coach may retrieve its own prior experiences
    against the same rival.
-   Do not let a coach read the result of a match before it makes its
    decision for that match.

The MVP's "learning" is retrieval and adaptation from stored
experiences, not model-weight training.

## 8. MongoDB Atlas data and persistence

MongoDB is the durable source of truth for application state. LLM
context and process memory are disposable.

Recommended collections:

  -----------------------------------------------------------------------
  Collection                          Purpose
  ----------------------------------- -----------------------------------
  `matches`                           Match metadata, seed, status,
                                      current half/step, score,
                                      authoritative state version

  `match_events`                      Append-only structured simulation
                                      events

  `coach_decisions`                   Analysis summaries, predictions,
                                      submitted plans, rationale,
                                      evaluation

  `tasks`                             Durable workflow/task state and
                                      checkpoint pointers

  `actions`                           Action ledger for each tactical
                                      command and its lifecycle

  `coach_experiences`                 Summarized, attributable past
                                      situations and outcomes, with
                                      embedding

  `worker_leases`                     Worker ownership, lease expiry,
                                      heartbeat, fencing token
  -----------------------------------------------------------------------

### 8.1 Persistence rules

-   Store structured state and event records; do not use chat transcript
    as the source of truth.
-   Give every match, event, task, decision, and action a stable unique
    ID.
-   Use append-only events for match history.
-   Store a `state_version` or equivalent optimistic concurrency value.
-   Persist checkpoints after meaningful workflow boundaries.
-   Store both the decision and its actual verified outcome.
-   Keep each coach's private experience namespace separate.
-   Use indexes on match ID, team ID, task ID, action ID, status, and
    timestamps.
-   Use MongoDB transactions only where supported and useful; do not
    assume a write to an external simulator and a MongoDB write can be
    one atomic transaction.

### 8.2 Vector Search

Use Atlas Vector Search on `coach_experiences` to retrieve similar
situations. Each experience should contain: - Coach/team namespace. -
Situation summary. - Structured context tags (formation, opponent style,
score state, fatigue band). - Decision taken. - Verified outcome. -
Embedding and model/version metadata.

Filter by coach namespace and relevant metadata before or alongside
vector similarity. Vector results are hints, not truth. Verify retrieved
claims against stored structured data when needed. If no suitable
experience exists, continue without retrieval.

## 9. Action verification and crash recovery

### 9.1 Action lifecycle

Every tactical action follows:

`proposed → submitted → applied → verified`

Terminal alternatives: `rejected`, `failed`, `unknown`.

-   `submitted` means a request was sent; it does **not** mean the
    simulation applied it.
-   `applied` means the simulator acknowledged the command.
-   `verified` means the worker read the authoritative simulation state
    and confirmed the requested settings are active.
-   An action with an uncertain result must be reconciled by reading
    actual state before retrying.

### 9.2 Idempotency

-   Create a stable `action_id` before sending an action.
-   The simulator must deduplicate repeated action IDs.
-   Retrying the same action ID must return the original result rather
    than apply it twice.
-   Use a unique index on `action_id`.
-   Store the expected state version and resulting state version.
-   If the simulator cannot support idempotency, reconcile current state
    before retrying; never blindly replay an uncertain command.

### 9.3 Crash detection

-   A worker periodically updates a heartbeat and renews its lease.
-   A separate recovery controller detects expired leases / stale
    heartbeats.
-   A heartbeat only indicates process liveness; also track task
    progress and checkpoint age.
-   Use a lease with an incrementing fencing token so a stale worker
    cannot commit after a replacement worker takes ownership.
-   Recovery loads the latest durable checkpoint and action ledger,
    reconciles uncertain actions against simulator state, then resumes
    from the first incomplete step.
-   Do not replay the full event history or repeat verified actions.

For the demo, include a deliberate crash injection point after action
submission but before verification. Show that the replacement worker
checks simulator state and safely completes reconciliation.

## 10. Environment and schema adaptation

The MVP should handle bounded, testable changes rather than promise
arbitrary adaptation.

Support at least: - A missing/unavailable player or invalid player ID. -
A tactical option removed from the allowed action schema. - An
unexpected optional field or changed event payload version.

Implementation: 1. Validate incoming state and simulator capabilities
against a versioned schema. 2. Detect unknown/missing required fields or
unsupported actions. 3. Fetch current capabilities/state from the
simulator. 4. Map the intent to a supported alternative where safe. 5.
If the intent cannot be safely mapped, ask the Tactical Coach for a
replacement plan. 6. Validate, execute, read back, and verify the
replacement. 7. Record the schema version, adaptation, and outcome.

Never silently reinterpret an invalid action. Preserve the original
intent and record the adapted action.

## 11. ElevenLabs voice experience

ElevenLabs is a presentation layer, not a source of match truth or a
decision-maker.

MVP voice features: - Generate a 20--40 second halftime briefing for
each coach. - Optionally generate short goal / full-time commentary. -
Provide text captions/transcript alongside audio. - Identify which coach
is speaking. - Use configured voice IDs from environment variables; do
not hardcode credentials or voice IDs. - Generate audio only after the
underlying analysis/decision is persisted. - Cache generated audio by
stable briefing ID to avoid duplicate generation. - If ElevenLabs is
unavailable, keep the text briefing and continue the match.

Suggested flow: 1. Coach produces structured plan and concise spoken
script. 2. Validate and persist the plan and script. 3. Call ElevenLabs
text-to-speech. 4. Store audio metadata / URL or object-storage key, not
large audio blobs in match documents. 5. Display audio player and
transcript.

Never synthesize or present fabricated events as actual match
commentary. Voice scripts must be grounded in persisted match facts and
coach decisions.

## 12. Evaluation harness

The harness is independent of both coaches and computes metrics from
structured simulation records.

### Core metrics

  -----------------------------------------------------------------------
  Metric                              Measurement
  ----------------------------------- -----------------------------------
  Match outcome                       Win/draw/loss and goal difference

  Tactical impact                     Change in relevant team/opponent
                                      metrics from first to second half

  Prediction accuracy                 Whether predicted rival changes
                                      matched actual changes

  Decision validity                   Percentage of plans accepted
                                      without fallback

  Execution reliability               Verified actions / attempted
                                      actions

  Recovery correctness                Successful resumes without
                                      duplicate verified effects

  Evidence grounding                  Claims supported by event IDs or
                                      structured metrics

  Latency / cost                      Decision duration and model/API
                                      usage
  -----------------------------------------------------------------------

Do not rank coaches by wins alone. Report metrics separately and use
repeated seeded matches with sides swapped to reduce starting-side bias.

### Fair comparison

-   Give both coaches the same public match information and decision
    deadline.
-   Use equivalent model/tool budgets and the same action constraints.
-   Keep private memories separate.
-   Run multiple seeds.
-   Swap teams/sides across paired runs.
-   Save the full configuration and seed for reproducibility.
-   The evaluator must not expose hidden future events to either coach.

## 13. User interface requirements

One dashboard is sufficient.

Required panels: 1. **Match view:** pitch representation, score, clock,
possession, shots, recent events. 2. **Coach comparison:** side-by-side
halftime analysis, predictions, tactics, and voice playback. 3.
**Timeline:** event stream, decisions, action lifecycle, verification,
recovery events. 4. **Evaluation:** coach metric comparison and match
results. 5. **Demo controls:** start match, run batch, inject crash,
reset match.

Use simple player markers and tactical labels. Fancy animation is
optional and must not block core functionality.

## 14. Suggested architecture

``` text
React + TypeScript Dashboard
             |
          FastAPI
             |
  Match Orchestrator / LangGraph
       /                 \
 Your Coach            Rival Coach
 Analyst                Analyst
 Tactical Coach         Tactical Coach
 Executor               Executor
       \                 /
        Simulation Engine
             |
    Action Verification
             |
       MongoDB Atlas
  matches / events / tasks
  actions / decisions / experiences
             |
     Atlas Vector Search

Recovery Controller ---> task leases / checkpoints
ElevenLabs ------------> voice briefings
Evaluation Harness ----> independent metrics
```

Use LangGraph only where its stateful graph workflow is useful. Keep
MongoDB's durable task/action records authoritative. Avoid adding a
separate graph database for the MVP.

### 14.1 Technology mapping

  -----------------------------------------------------------------------
  Requirement                         Technology
  ----------------------------------- -----------------------------------
  Coordinate multiple agents          LangGraph

  Save agent execution state          MongoDB Checkpointer (LangGraph)

  Remember previous matches           MongoDB Store (LangGraph)

  Find similar tactical situations    Atlas Vector Search

  Detect match changes                MongoDB Change Streams (optional
                                      for the initial MVP; see §3)

  Verify tactical actions             Custom action ledger (`actions`
                                      collection, §9)

  Generate spoken coaching            ElevenLabs
  -----------------------------------------------------------------------

**Checkpointer vs. action ledger:** the MongoDB Checkpointer saves
LangGraph workflow state, but it does not independently guarantee that
an external tactical action happened. The action ledger and match-state
verification (§9) remain responsible for confirming that a tactical
action was actually applied to the simulator.

### 14.2 Data sources

  -----------------------------------------------------------------------
  MVP component                       Data source
  ----------------------------------- -----------------------------------
  Match analyst                       StatsBomb events

  Opposition scout                    StatsBomb + Metrica

  Formation and positioning analysis  Metrica tracking

  Historical tactical memory          StatsBomb-derived match summaries

  Rival coach strategy                LLM + match observations

  Second-half simulation              Custom Python engine

  Evaluation harness                  Simulated outcomes + historical
                                      benchmarks

  ElevenLabs voice                    Generated coaching reports
  -----------------------------------------------------------------------

## 15. Recommended implementation phases

### Phase 0 --- Foundation

-   Create repository, configuration, typed schemas, and environment
    template.
-   Implement MongoDB connection and repository layer.
-   Add deterministic seed handling.

**Exit criteria:** Application starts and persists a test match.

### Phase 1 --- Simulation

-   Implement two teams, match clock, event generation, score, and
    tactical parameters.
-   Implement halftime and full-time transitions.
-   Add repeatable seeded simulations.

**Exit criteria:** Same seed/config produces reproducible match results.

### Phase 2 --- Competing coaches

-   Implement analyst and tactical coach for each side.
-   Validate structured tactical output.
-   Apply plans to the second half.
-   Add rival prediction.

**Exit criteria:** Both coaches produce different valid plans and those
plans affect match behaviour.

### Phase 3 --- Memory and recovery

-   Persist checkpoints, actions, leases, and verified outcomes.
-   Add Vector Search retrieval for prior experiences.
-   Add crash injection and reconciliation.

**Exit criteria:** Crash after submission does not duplicate an action
or replay completed work.

### Phase 4 --- Voice and evaluation

-   Add ElevenLabs briefings with text fallback.
-   Implement repeated-match evaluation and side swaps.
-   Build comparison dashboard and demo controls.

**Exit criteria:** One-click demo runs, speaks, evaluates, and shows
recovery.

## 16. Definition of done

The MVP is complete when all of the following pass:

-   [ ] A seeded match runs from kickoff to full-time.
-   [ ] Two independent coaches analyze the same public match data.
-   [ ] Both coaches submit schema-valid tactical plans.
-   [ ] The plans alter second-half simulation behaviour.
-   [ ] Each coach predicts the rival's likely tactical adjustment.
-   [ ] Coach memories are private and Vector Search retrieval is
    filtered correctly.
-   [ ] Match events, decisions, checkpoints, and actions persist in
    MongoDB.
-   [ ] An action is not considered successful until its effect is read
    back and verified.
-   [ ] A crash after submission is recovered without duplicating the
    effect.
-   [ ] A stale worker is prevented from writing after lease
    reassignment.
-   [ ] At least one bounded schema/capability change is handled safely.
-   [ ] ElevenLabs generates a halftime briefing, with text fallback if
    unavailable.
-   [ ] The evaluator compares both coaches across multiple seeded,
    side-swapped matches.
-   [ ] The UI shows match state, decisions, voice, recovery, and
    evaluation.

## 17. Engineering principles

1.  **Simulation is the source of match truth.** LLMs interpret and
    recommend; they do not invent match facts.
2.  **Structured state beats chat history.** Persist typed records and
    checkpoints.
3.  **Verify effects, not requests.** An API response is not proof of
    the final state.
4.  **Make retries safe.** Stable action IDs, idempotency,
    reconciliation, and fencing.
5.  **Keep coaches independent.** Separate memory namespaces and
    prompts.
6.  **Evaluate with evidence.** Use reproducible seeds and measurable
    outcomes.
7.  **Fail gracefully.** Voice, Vector Search, and LLM failures must not
    prevent the simulator from finishing.
8.  **Build the smallest convincing demo first.** No live-data
    integrations or unnecessary infrastructure.
